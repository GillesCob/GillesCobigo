Après le week-end, retour à la liste de dette technique de _Cerithe_ posée après la livraison du MVP. [Le dernier article de la série se terminait sur une phrase simple](/articles/2026-07/260724) : le prochain sujet, ce sont des tests qui n'existent toujours pas.

Sauf qu'avant d'écrire le premier, j'ai buté sur une question à laquelle je n'avais pas de réponse toute faite : tester quoi, exactement, sur une fonction que je n'ai pas écrite ligne par ligne moi-même ?

Toute la validation faite sur _Cerithe_ jusque-là s'est passée à la main, en conditions réelles, sur mon téléphone ou dans le navigateur. Ça a marché, jusqu'à un certain point. Mais un test manuel ne se rejoue pas tout seul à chaque changement. Et le pipeline de déploiement automatique prévu plus loin dans la liste n'aura rien à bloquer sans un vrai filet dessous.

## Le problème : personne n'avait encore dit ce qu'un test devait garantir

La tentation, en découvrant qu'une fonction n'est pas testée, c'est de se dire "il faut la tester" et de foncer. Sauf qu'un test, c'est une affirmation sur ce que le code doit faire. Si je choisis seul quoi vérifier, je vais couvrir ce qui me saute aux yeux à moi, en tant que dev, pas forcément ce qui compte vraiment côté métier.

La fonction visée en premier gère la création d'une transmission, l'action qui déclenche tout le processus de vente d'un bien sur _Cerithe_. Avant d'écrire quoi que ce soit, il a donc fallu répondre à une question plus large : qu'est-ce qui doit rester vrai, dans tous les cas, pour que cette fonctionnalité reste fiable ?

## Lister ce qui peut casser avant la moindre ligne de test

J'ai listé le scénario nominal et les cas qui me semblaient évidents : le destinataire avec plusieurs profils, le refus possible, l'annulation à tout moment côté propriétaire, une seule transmission active par bien. En relisant cette liste avec Claude Code, plusieurs cas supplémentaires sont apparus, déjà présents dans le code mais que je n'avais pas identifiés comme des cas à part entière : l'impossibilité de se transmettre un bien à soi-même, la vérification que l'appelant est bien le propriétaire du bien, deux messages d'erreur différents selon l'état bloquant et surtout un vrai bug déjà corrigé en juillet, où le profil du destinataire restait introuvable s'il s'inscrivait après coup.

Ce dernier point, c'était le plus important à couvrir. Un bug déjà survenu une fois en prod, jamais protégé depuis par un test qui empêcherait qu'il revienne un jour sans qu'on s'en aperçoive.

## Deux choix techniques, deux justifications à assumer

Une fois la liste posée, restaient deux décisions à prendre avant d'écrire quoi que ce soit. La première : quel outil pour faire tourner ces tests. _Cerithe_ tourne entièrement en ESM, le système de modules natif de JavaScript, un choix déjà fait depuis juin pour éviter les frictions avec des outils plus anciens. Vitest colle nativement à ce fonctionnement, sans configuration à rajouter. Jest, l'alternative la plus connue, aurait demandé un ajustement spécifique pour s'en accommoder.

La deuxième décision compte plus que la première : un test unitaire ne doit dépendre de rien d'autre que le code qu'il vérifie, ni base de données, ni réseau. Toutes les requêtes vers la base sont donc entièrement simulées.

```ts
vi.mock("../lib/prisma", () => ({ default: mockDeep<PrismaClient>() }));
```

Le mécanisme exact de cette simulation, je le laisse pour l'instant à Claude Code : la priorité est ailleurs. Ce qui compte, c'est le principe. Un test qui touche à la base réelle change de nature : ça devient un test d'intégration, un exercice différent, déjà prévu plus loin dans la liste.

Résultat, dix tests qui isolent chacun un seul cas, du genre le plus lisible possible :

```ts
await expect(createTransmissionToken(ownerEmail, ownerId, propertyId)).rejects.toThrow(
  "L'email du destinataire est le même que le propriétaire actuel du bien.",
);
```

## Ce que j'en retiens

Dix tests qui passent, sur une seule fonction parmi sept. Loin d'être fini. Ce qui compte aujourd'hui : la liste des cas est venue de moi avant la moindre ligne de test et chaque test dit exactement ce qu'il garantit, sans ambiguïté.

Un test mal pensé donne une fausse confiance, pire qu'aucun test du tout. Avant de se demander comment tester, il faut toujours se demander quoi et pourquoi celui-là plutôt qu'un autre.

La suite de la dette : faire tourner ces tests automatiquement à chaque push, avant que le code n'atteigne le VPS.
