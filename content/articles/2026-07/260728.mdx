Le dernier article se terminait sur une annonce : faire tourner les tests automatiquement à chaque push, avant que le code n'atteigne le VPS. Sauf qu'avant de toucher au moindre fichier de configuration, une session entière est passée à reposer les bases du CI/CD. Un des termes les plus employés et les moins définis avec précision du métier, je m'en servais moi-même sans tracer la frontière exacte entre ses morceaux.

## Le problème : je ne voulais pas automatiser un mécanisme que je ne maîtrisais pas

Le déploiement de _Cerithe_ tient aujourd'hui en deux commandes tapées à la main sur le VPS : un `rsync` qui copie le code, un rebuild Docker qui le fait tourner. Ça fonctionne, mais rien ne garantit que le code copié est sain avant qu'il ne tourne en prod. Le prochain item de la dette technique, c'est justement ça : un pipeline qui bloque le déploiement si les tests échouent, plutôt qu'un déploiement aveugle.

Écrire cette configuration sans comprendre chaque étape reviendrait à automatiser à l'aveugle plutôt que déployer à la main à l'aveugle.

## CI, CD, Delivery, Deployment : remettre les mots à leur place

Le CI, l'intégration continue, est la partie la plus simple à cerner. À chaque push, une machine récupère le code, installe les dépendances et fait tourner les vérifications automatiques, les tests en premier lieu. Son seul rôle est de rendre un verdict : ça passe ou ça casse.

La confusion commence avec le CD, deux pratiques distinctes sous un seul nom. La livraison continue prépare tout automatiquement jusqu'à un artefact prêt à partir en prod, une image Docker par exemple, mais laisse un humain décider du moment. Le déploiement continu va plus loin : dès que les tests passent, l'artefact part en prod sans validation humaine, un sur-ensemble de la livraison plutôt qu'une pratique concurrente.

## Le pipeline visé pour Cerithe

Seul développeur sur _Cerithe_, main déjà branchée en direct sur la prod, le déploiement continu a plus de sens que la livraison continue : rien ne justifie un clic manuel entre des tests qui passent et la mise en prod.

Le schéma ci-dessous, produit pour mon rapport de fin de formation, illustre le mécanisme canonique du CI/CD par image. Il est bâti sur GitLab CI/CD, _Cerithe_ tournera sur GitHub Actions, mais les concepts derrière sont identiques, seul l'outil change.

![Schéma CI/CD : intégration continue à gauche (build, tests, construction des images), déploiement continu à droite (registre, service de déploiement)](/imagesArticles/2026/07/28/1.png)

Détail à souligner : une image ne part jamais directement de la machine qui la construit vers le serveur, elle transite d'abord par un registre. Et le point qui structure tout le reste, le job qui construit et déploie ne se déclenche que si celui des tests a réussi.

```yaml
jobs:
  test:
    # installe les dependances, fait tourner npm run test
  deploy:
    needs: test
    # ne demarre que si le job test a reussi
```

## Deux façons de déployer et pourquoi je reste sur la plus simple

Le schéma plus haut illustre un déploiement par registre : une fois les tests passés, GitHub Actions construit l'image, la pousse vers un registre, puis le VPS la récupère et bascule dessus. Le serveur qui sert le trafic réel ne construit jamais rien lui-même.

L'autre option, plus proche de ce qui se fait déjà à la main sur _Cerithe_ : GitHub Actions se connecte en SSH au VPS une fois les tests passés et y relance le rebuild déjà pratiqué manuellement. La différence qui compte le plus : dans la première option, le serveur de prod ne fait jamais tourner de compilation, seulement un téléchargement et un redémarrage de conteneur. Dans la seconde, la construction se déroule sur la machine qui sert aussi le trafic réel.

Je pars sur la seconde option, pour l'instant. Pas parce qu'elle est la plus aboutie, mais parce qu'elle applique [le principe posé en retirant la branche `dev` du circuit Git](/articles/2026-07/260724) : une pratique se justifie par un problème réel qu'elle résout, pas par sa réputation. Le VPS n'a jamais montré le moindre signe de saturation pendant un déploiement et _Cerithe_ reste un projet mono-instance à faible trafic.

Deux signaux feraient basculer ce choix plus tard : un déploiement qui ralentit visiblement le site en prod, ou le besoin de faire tourner _Cerithe_ sur plusieurs serveurs à la fois.

## Ce que j'en retiens

Reposer ces bases avant d'écrire le moindre fichier de configuration a changé une chose : je sais maintenant ce que chaque étape du pipeline doit garantir, pas seulement ce qu'elle doit faire tourner. Comprendre la théorie ne suffit pas à faire tourner un pipeline, mais foncer sans elle revient à débugger à l'aveugle le jour où quelque chose casse.

La pratique arrive demain : connecter GitHub Actions au VPS en SSH et écrire le premier fichier de workflow qui fait vraiment tourner ce qu'on vient de décrire ici sur le papier.
